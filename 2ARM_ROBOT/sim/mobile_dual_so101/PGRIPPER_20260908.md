# NORMA PGripper 반영과 집기·인계·내려놓기 — SIM 검증 기록

record_id: DAPIER-2026-09-08-right-pgripper-simulation

나는 9월 8일 오른팔을 [NORMA PGripper](https://github.com/norma-core/norma-core/tree/b935fc4b887e576538921b15630a30db22759ec8/hardware/pgripper)로
교체한 구성을 SIM에 반영했다. 9월 9일 요청에 따라 **SIM의 왼팔도 동일한 PGripper와
카메라 장착 기준으로 전환**했다. 실물 왼팔 교체·보정은 확인하지 않았다. 팔에 달려 있던
실물 손목 카메라 세트는 그대로 유지하며, SIM 배치는 추가로 받은 체결 사진을 기준으로
추정했다. 이번 코드는 이 구성을 MuJoCo에서 확인하는 단계다.
실물 모터·카메라를 열거나 calibration을 바꾸는 명령은 실행하지 않았다.

## 찾은 원본과 적용 범위

PGripper 폴더에는 STL/STEP이 있고 독립 URDF는 찾지 못했다. 같은 저장소의
[ElRobot simulation URDF](https://github.com/norma-core/norma-core/blob/b935fc4b887e576538921b15630a30db22759ec8/hardware/elrobot/simulation/elrobot_follower.urdf)에서
base·motor·gear·jaw 2개로 된 subtree를 찾았다. 해당 다섯 STL, 원본 URDF와 hardware
Apache-2.0 라이선스를 `assets/norma_pgripper/upstream/`에 원형 보존하고 SHA-256을 기록했다.
전체 ElRobot의 나머지 링크 mesh는 복사하지 않았으므로 그 URDF 자체는 전체 로봇 실행용이 아니다.

인쇄용 jaw와 simulation jaw를 강체 정렬해 비교하니 simulation vertex의 최대 차이는
약 0.000036mm였다. 삼각형 수는 다르지만 확인한 기하학적 특징은 일치했다.
이번 것은 **공식 SO-101용 URDF를 발견한 결과가 아니라 원본 형상을 옮긴 adaptation**이다.
이후 SO-101 장착 URDF를 받아 체결 위치·회전을 대조했다. 추가 반영은 아래 9월 9일 절에 기록했다.

| 구성 | 왼팔 | 오른팔 | 용도 |
| --- | --- | --- | --- |
| `stock` | 기본형 | 기본형 | 기존 녹화·ACT·회귀 검사 보존 |
| `right` | 기본형 | PGripper | 현재 교체 상태의 SIM |
| `both` | PGripper | PGripper | 현재 요청한 양손 SIM 구성·인계 실험 |

기존 mobile/compact/tabletop builder는 `grippers=`를 받되 stock 기본값을 유지한다.
새 `pgripper_sim.py`는 9월 9일부터 both가 기본이다. 기존 LeRobot fork·원본 XML/STL·ROS URDF는
수정하지 않고 불러온 MuJoCo spec에서만 교체한다. RoboTwin/SAPIEN 실행기와 과거 ACT는
이번에 새 그리퍼로 전환하지 않았다. 과거 성공 결과도 PGripper 결과로 바꾸어 읽지 않는다.

## 기구·단위·충돌

좌 6축→우 6축, actuator 총 12개는 유지한다. 교체한 팔마다 passive prismatic joint
2개와 joint equality 2개가 추가된다. 물체를 붙이는 weld는 없다.

```text
q_open = 2.2028 - upstream_motor_angle  [rad]
jaw travel per side = 0.0115 × upstream_motor_angle  [m]
inner-face gap ≈ 0.000368878 + 0.023 × q_open  [m]
```

`data.ctrl`의 새 집게 값은 opening-positive rad이며 0은 명목 닫힘, 2.2028은 최대 열림이다.
정규화 정책 경계의 0..1과 혼동하지 않는다. 이 SIM 좌표를 실물 tick이나 예전 녹화의
0..100에 그대로 대응하지 않는다. `recorded_to_sim`/`sim_to_recorded`는 PGripper 모델에
기본형 녹화를 넣으면 거부한다. 향후 정책 연결 때 새 그리퍼·보정·dataset·checkpoint
revision을 명시적으로 묶어야 하며 범용 action normalizer만으로 호환성을 판단하지 않는다.

원본 URDF 기준 총 이동량은 **50.6644mm**다. 최대 개구는 약 **51.0333mm**, 명목 닫힘에도
약 **0.3689mm**가 남는다. README의 54mm는 광고된 총 travel이므로 이 값을 맞추려고
CAD나 기어 비율을 임의 확대하지 않았다. 실제 개폐 끝점과 장착 방향은 별도 측정한다.

손끝 접촉은 distal CAD vertex의 convex hull로 만들어 가늘어지는 윤곽을 보존한다.
첫 사각형 proxy는 실제 tip보다 한쪽으로 약 8.125mm 넓어지는 문제가 있어 교체했다.
housing은 box이며 손가락 전체·rack·gear tooth 접촉은 모델링하지 않는다. 따라서 전체
충돌 정확도나 파지 성능은 미검증이다. 공통 충돌 guard는 교체된 housing과 양쪽 pad를
필수로 검사하고 하나라도 비활성화하면 거부한다. 기본형의 기존 검사도 유지한다.

초기 장착은 horn 중심·축 정렬 가정이었고, 현재는 제공받은 SO-101 URDF의 체결 좌표를 쓴다.
TCP는 양쪽 내측 면의 중간점으로 개폐 중 위치가
변하지 않는다. 원본 질량·관성을 변환하되 0으로 제공된 작은 gear 관성만 CAD bbox로
근사했다. 마찰·gain·effort·damping·실제 mount 오차는 동특성 식별값이 아니다.
초기에는 기존 camera 상대 pos/quat/FOV를 유지했다. 현재 PGripper camera는 사진 기반의
별도 추정 배치이며 실측 외부 보정은 확인 전이다.

## 재현과 초기 반영 결과 — 9월 8일

기존 MuJoCo·LeRobot·Arrow·Pillow 환경을 사용하며 새 의존성은 추가하지 않았다.
아래 `python`은 그 환경의 실행 파일로 바꾸고 XML은 인접 assets가 있는 기존 기본형을 지정한다.
출력 경로는 존재하지 않는 새 디렉터리를 쓴다.

```bash
export DAPIER_SO101_MJCF=/absolute/path/to/so101_new_calib.xml
MUJOCO_GL=egl python 2ARM_ROBOT/sim/mobile_dual_so101/pgripper_sim.py \
  --grippers right --output /tmp/new-pgripper-right
MUJOCO_GL=egl python 2ARM_ROBOT/sim/mobile_dual_so101/pgripper_sim.py \
  --grippers both --output /tmp/new-pgripper-both
python -m unittest discover -s 2ARM_ROBOT/sim/mobile_dual_so101/test \
  -p test_pgripper.py -v
```

`--viewer`를 추가하면 SIM 전용 native Control panel을 최대 30분 연다. GUI를 사용할 때는
설치 환경의 GUI backend를 사용한다. 자동 실행에서는 GUI를 열지 않고 EGL로 렌더했다.
MJCF는 mesh의 절대 경로를 참조하므로 자산 폴더를 옮기면 다시 생성한다. MJCF 안의
`home` keyframe을 선택해야 보고서의 시작 자세가 된다. `MjData` 기본값만 쓰면 같은 자세가 아니다.

- MuJoCo **3.8.1·3.3.7**에서 새 통합 검사 2개 모두 통과했다. stock/right/both의
  12축 계약, passive coupling, 양팔 개폐, camera 보존, 저장 MJCF 재열기를 확인했다.
- 3.8.1에서 기본 mobile 14개·compact 12개·policy 4개·collision guard 10개가 통과했다.
- 기본형 `test_tabletop_physics.py`도 다시 실행했다. 책상 집기·3초 유지, 처음부터
  접촉 제거 시 획득 실패, 획득 후 접촉 제거 시 낙하가 통과했다. 기존 결과를 새 그리퍼
  결과로 바꾸지 않고 `recording/simulation/20260908/stock-after-pgripper/`에 따로 남겼다.
- 새 개폐 실행은 초기화 한 번 뒤 `data.ctrl`과 `mj_step`만 사용했다. 1,500 step 동안
  warning 0·유한 상태였고 오른팔 장면은 `nq=21, nv=20, nu=12, neq=2`다.
- right 구성의 왼팔 body pose·질량·관성과 control range는 기본형과 같았다.
  tabletop camera pos/quat/FOV와 compact camera pos/quat도 같았다.
- 새 폴더에 MJCF·열림/닫힘 PNG·`report.json`을 생성하고 MJCF를 다시 불러왔다.
  PNG는 **pose-only**다. 물리 trace도 물체를 집지 않는 개폐 smoke이며 파지 성공 근거가 아니다.

실행 결과는 비공개 `recording/simulation/20260908/pgripper-right-final/`과
`pgripper-both-final/`에 두었다. `sim_to_real_valid=false`, `grasp_success_verified=false`,
`hardware_execution=false`를 유지한다. 다음은 최종 장착 확인→카메라 보정→새 개폐/TCP
측정→집기·접촉 제거 대조→새 데이터와 정책 검증 순서다.

## 제공 URDF와 사진 기반 체결·카메라 반영 — 9월 9일

제공받은 `so101_pgripper.urdf`의 11개 link와 10개 joint, STL 참조를 확인했다.
그리퍼 STL 5개는 이미 보존한 NORMA 파일과 SHA-256까지 같았다. 원본을 MuJoCo 3.3.7에
직접 넣으니 gear의 0 관성 때문에 로딩이 실패했다. 메모리에서 관성만 임시 보완한 진단에서는
`nq=8, nu=0, neq=0`이어서 URDF의 mimic만으로는 MuJoCo 손가락 연동이 생기지 않았다.
따라서 검증한 기존 관성 보완·actuator·equality를 재사용하고 체결 좌표만 반영했다.
원본 ZIP과 사진은 수정하거나 배포하지 않았다.

손목 기준 위치는 `[0, -0.0611, 0.0181] m`, URDF RPY는
`[3.14151353, 1.52211682, -0.00007819] rad`다. 초기 모델과 약 89도 다른 자세다.
source→canonical 기하 변환을 되돌려 이 자세를 적용하며, 회전축도 같은 변환으로 옮겼다.
그리퍼만 돌리고 wrist joint 축을 기존 +Z에 남기는 오류를 피했다. 실제 encoder zero를
측정하거나 실물 보정 파일을 바꾼 것은 아니다.

사진에서 확인한 작은 사각 PCB·긴 브래킷 형태를 따라, 같은 NORMA revision의
`CameraMount_square_27mm.stl`을 재사용했다. 27mm는 장착 구멍 간격이며 실제 장치 모델을
확인했다는 뜻은 아니다. 브래킷 형상 치수는 CAD에서 가져왔지만 체결 자리와 광학 중심은 추정이다.

| 항목 | 현재 SIM 값 | 근거·한계 |
| --- | --- | --- |
| 브래킷 원점 | `[0, -23.450, 0] mm` | 그리퍼 housing 옆면·손목 쪽 끝에 놓은 사진 기반 추정 |
| 카메라 광학 중심 | `[0, -68.761, -6.831] mm` | CAD PCB 지지면에서 렌즈 방향으로 8.5mm; 미측정 |
| 시선 방향 | `[0, 0.422618, -0.906308]` | 브래킷 면의 25도 기울기, 집게 끝 방향 |
| 수직 FOV | `75°` | 기존 가정 유지; intrinsics 미보정 |

좌표는 `pgripper.py`가 정규화한 그리퍼 기하 좌표계다. `provenance.json`의
`so101_mount`와 `wrist_camera`에서 값·출처·미검증 상태를 함께 관리한다. PCB/렌즈는
visual-only 근사이며 카메라 질량·브래킷 충돌은 추가 모델링하지 않았다. 이미지의 위쪽 방향도
실제 센서 프레임과 대조하지 않았으므로 image roll까지 보정됐다고 보지 않는다.

카메라는 그리퍼에 고정되어 함께 움직인다. compact 장면의 박스 자동 조준은 PGripper에
적용하지 않는다. 오른팔 교체 시 왼팔 기본형과 top camera는 그대로 유지한다.

- MuJoCo 3.3.7·3.8.1에서 갱신한 PGripper 통합 검사 **3개씩 통과**했다.
- wrist roll `-0.5, 0, +0.5 rad`에서 제공 URDF의 회전과 일치하고, 카메라 상대 위치와
  시선이 유지되며 집게 TCP가 FOV 안에 있는지 검사했다. stock/right/both coupling도 통과했다.
- 3.8.1의 stock compact 12개·collision guard 10개가 통과했다.
- 오른팔 모델을 1,500 step 개폐해 warning 0, MJCF 저장·재로딩 성공을 확인했다.
  열림 약 51.0333mm·닫힘 약 0.3689mm로 기구 비율은 유지됐다.
- 전체 브래킷이 보이는 외부 렌더와 `right-wrist-open/closed.png`를 직접 확인했다.
  이 PNG는 pose-only이고 물체 파지 성공이나 실물 카메라 일치의 증거가 아니다.

새 결과는 비공개 `recording/simulation/20260909/pgripper-photo-urdf-right/`에 보존했다.
사진만으로 mm/각도 오차를 산출할 수 없으므로 `camera_mount_measured=false`,
`physical_mount_verified=false`, `sim_to_real_valid=false`를 유지한다.

## 동일한 양손 PGripper의 접촉 기반 인계 — 9월 9일

record_id: DAPIER-2026-09-09-dual-pgripper-handover

`pgripper_handover.py`에서 동일한 모델·카메라를 양쪽에 적용하고, 4cm·약 20g 자유 강체를
책상에서 집어 반대 손으로 넘겼다. 좌우 각각 새 실행을 시작해 양방향을 검증했다.
한 실행에서 연속 왕복하는 정책이나 카메라 인식 기반 자율 인계는 아니다.
실제 task와 기본 실행 방향은 **왼팔 → 오른팔**이다. 반대 방향은 추가 회귀 검증용이며,
`--donor right --handover-only`로 명시했을 때만 실행한다. 기본 실행은 아래의
왼손 집기 → 오른손 인계 → 오른손 내려놓기까지 진행한다.

흐름은 집기 → 인계 자세로 운반 → 받는 손을 빈 공간에서 회전 → 접근·삽입 →
받는 손의 양쪽 접촉력 확인 → 주는 손 열기·후퇴 → 받는 손 단독 3초 유지다.
집게를 닫는 목표는 1.5N, 승인 조건은 **양쪽 패드 각각 1N 이상을 연속 0.33초**다.
놓은 뒤에는 받는 손의 접촉력을 계속 보정한다. 3초 유지 검사는 2ms 물리 스텝마다
받는 손 양쪽 접촉력 ≥0.3N, 주는 손 접촉력 ≤0.01N, 블록 중심 높이 >60mm를 확인한다.
전 구간에서 10N 초과, 1mm 초과 관통, 팔끼리·자체·책상 충돌과 물리 경고를 차단한다.
주는 손을 여는 중에도 받는 손의 양쪽 힘이 0.3N 아래로 떨어지면 중단한다.
열림 완료와 주는 손 접촉 해제까지 확인해야 `donor_released=true`를 기록한다.

처음에는 받는 손의 접근 방향을 주는 손의 개폐축과 맞춰 손끝이 겹쳤다. 주는 손
**패드의 폭 방향**으로 접근하도록 바꾸고, 공통 블록 중심을 약 `[.27, 0, .17] m`로
옮기니 기존 충돌 형상을 유지하며 인계 자세를 얻었다. 경로의 고정 joint waypoint는
이 장면 전용 offline IK 결과다. 블록 위치 정답은 검증 로그에만 쓰며 제어 목표로 읽지 않는다.
실행 중 물체 pose 재설정·weld·mocap·외력 부착은 없다.

일정한 접촉력에서도 느린 수치 미끄러짐이 보여 인계 실행에만 `impratio=10`을 사용했다.
이는 MuJoCo의 마찰 방향 constraint impedance 설정이며 마찰계수나 형상을 바꾸지 않는다.
`noslip_iterations=0`은 유지했다.
[MuJoCo 접촉 설정 설명](https://mujoco.readthedocs.io/en/3.3.7/XMLreference.html#option-impratio)을
참고했으며 실측 재료 물성으로 보정한 값은 아니다. 기존 stock replay 설정은 유지한다.

MuJoCo 3.3.7의 접촉 보정 적용 실행:

| 방향 | 인계·단독 유지 | 최종 블록 중심 높이 | 최대 관통 | 물리 경고 |
| --- | --- | --- | --- | --- |
| 오른손 → 왼손 | 성공·3초 | 168.58mm | 0.0320mm | 0 |
| 왼손 → 오른손 | 성공·3초 | 168.09mm | 0.0297mm | 0 |

재현 명령은 다음과 같다. 출력은 항상 새로운 폴더를 지정한다.

```bash
export DAPIER_SO101_MJCF=/absolute/path/to/so101_new_calib.xml
python 2ARM_ROBOT/sim/mobile_dual_so101/pgripper_handover.py \
  --handover-only --output /tmp/new-pgripper-handover-left
python 2ARM_ROBOT/sim/mobile_dual_so101/pgripper_handover.py \
  --donor right --handover-only --output /tmp/new-pgripper-handover-right
python 2ARM_ROBOT/sim/mobile_dual_so101/pgripper_handover.py \
  --disable-recipient-contact --output /tmp/new-pgripper-handover-negative
python -m unittest discover -s 2ARM_ROBOT/sim/mobile_dual_so101/test \
  -p test_pgripper_handover.py -v
```

`--viewer`는 실제 물리 실행을 보여주고 끝 상태를 최대 30분 일시 정지해 둔다.
`--render`는 성공한 최종 물리 상태의 외부·좌우 손목 이미지를 저장한다.
negative 실행은 받는 손의 접촉만 끄며, 접촉 확인 시간초과와 해제 금지로 종료 코드 2가
나와야 한다. 회귀 테스트는 양방향 성공 후 받는 손의 접촉을 제거했을 때 40mm 이상
낙하하는지도 별도로 확인한다.

인계 전용 단계의 회귀에서는 MuJoCo **3.3.7·3.8.1 각각 인계 테스트 2개와 기존 PGripper 테스트
3개가 모두 통과**했다. 인계 통합 테스트 안에서 양방향 성공, 받는 손 접촉 비활성화,
해제 시작 직후 접촉 신호 상실을 실행했다. 양방향 성공 상태에서 접촉 제거 후 낙하도
확인했다. 해제 도중 신호 상실 시 `donor_release_started=true`,
`donor_released=false`로 중단되는 것을 검사했다.

아직 남은 것은 실물 장착·카메라 보정, 실제 센서로 접촉 판정을 대체하는 방법,
다른 블록 자세에 대한 인식·경로 계획과 새 학습 데이터다. 카메라 브래킷·rack 전체는
충돌 모델에 포함되지 않는다. `camera_driven=false`, `learned_ACT=false`,
`hardware_execution=false`, `sim_to_real_valid=false`를 유지한다.

## 실제 task 순서: 왼손 집기 → 오른손 인계 → 오른손 내려놓기

나는 인계만 보여주던 실행에 오른손 내려놓기를 추가하고 이 3단계를 기본값으로 바꿨다.
놓을 정확한 위치는 아직 지정하지 않아, 이번 고정 장면에서는 오른팔 앞쪽의
블록 중심 `[.22, -.08, .02] m`를 기준으로 사용했다. 양팔 PGripper와 카메라 구성은 같다.

오른손 단독 3초 유지 이후 집게를 아래로 향하게 회전하고, TCP를 높이 60mm로 접근시킨다.
천천히 내려가다 **블록–테이블 접촉력 0.1N 이상**을 처음 확인하면 하강을 멈춘다.
이후 0.2초 동안 지지력이 0.05N 이상 유지되어야 오른손을 연다. 지지가 없거나 끊기면
놓기를 시작하지 않는다. 연 뒤 30mm 후퇴하고, 3초 동안 네 패드 접촉력 ≤0.01N,
테이블 지지력 ≥0.1N, 블록 중심 높이 19–22mm, 이동 속도 ≤10mm/s를 매 물리 스텝 검사한다.
여기까지 통과해야 `task_success=true`다. `handover_success=true`만으로는 전체 task 성공이 아니다.

MuJoCo 3.8.1의 첫 전체 실행은 126.35 SIM초에 완료했다. 최종 블록 중심은
`[.218698, -.079277, .020000] m`, 테이블 단독 지지 검사는 3초 통과,
최대 관통은 블록–테이블의 0.1243mm, 물리 경고는 0이었다.
외부 렌더에서 블록이 테이블 위에 있고 양손 집게가 떨어진 것을 직접 확인했다.
결과는 비공개 `recording/simulation/20260909/pgripper-three-stage-01/`에 보존했다.

```bash
export DAPIER_SO101_MJCF=/absolute/path/to/so101_new_calib.xml
python 2ARM_ROBOT/sim/mobile_dual_so101/pgripper_handover.py \
  --viewer --render --output /tmp/new-pgripper-left-right-place
```

`--handover-only`는 내려놓기 전 단독 파지를 검사하는 진단 모드다. 반대 방향 인계도
이 모드에서만 허용한다. 실행 중 물체 pose를 옮기거나 붙이지 않고 모터 제어와 접촉으로
진행한다. 이 결과도 **고정 장면·가상 접촉 센서의 SIM baseline**이며 실물 성공이 아니다.

## 다음 고도화: RGB-D 1차 위치 → 좌우 손목 카메라 최종 보정

현재 결정은 RGB-D로 블록의 대략적인 3D 위치를 먼저 구하고, 가까이 접근한 다음
왼팔·오른팔에 달린 카메라로 최종 위치를 보정해 찾아가는 것이다.
왼손 집기에서는 왼쪽 손목 영상을, 인계에서는 양쪽 손목 영상을 이용해 상대 위치와
받는 손 정렬을 확인하는 방향으로 개발한다. 내려놓기에서도 오른쪽 손목 관측을 연결한다.

RGB-D의 metric depth·intrinsics·외부 보정으로 공통 좌표와 양팔 좌표의 초기 목표를 만들고,
손목 RGB의 영상 오차와 관절 FK를 결합해 가까운 구간을 보정한다. 손목 RGB만으로
절대 깊이가 측정된다고 가정하지 않는다. 최종 보정 결과는 접근 목표를 갱신하며,
받는 손의 파지 확인과 테이블 지지 확인을 대체하지 않는다. 실제 접촉 센서가 없다면
이를 무엇으로 판정할지도 실물 전환 전에 검증해야 한다.

영상 시간·보정 revision·추적 신뢰도를 확인하고, 영상이 오래됐거나 가려져 추적이 끊기면
전진/해제하지 않고 재관측하는 조건을 추가할 예정이다. 이번 task 실행은 아직 이 인식
경로를 사용하지 않는다. 고정 목표를 쓰는 baseline을 남겨 두고 이후 관측 기반 목표로
교체하며, `camera_driven=false`는 실제 카메라 입력 연결과 검증 전까지 유지한다.

## 중간 정지 줄이기와 오른손 실측 자료 대조

동작 중 멈춘 듯 보이는 구간을 줄여 달라는 요청에 따라 매 이동 뒤의 0.3초 대기,
집기 뒤의 별도 3초 대기와 인계 자세의 1초 대기를 제거했다. 받는 손의 단독 파지 3초
검사는 주는 손이 후퇴하는 동안 매 스텝 수행한다. 검증 시간을 없애지 않고 빈 팔의
후퇴와 겹쳤다. 접촉 확인 0.33초, 테이블 지지 확인 0.2초와 최종 안정 검사 3초는 유지한다.

빈 공간 닫힘은 0.20rad/s, 접촉 후에는 0.04rad/s로 제한했다. 고정된 위치 명령만
유지하면 역방향 집기에서 들어 올리는 동안 접촉력이 떨어져, 파지 중인 **양손 모두**에
기존 유지 제어를 적용했다. 유지 목표는 1.5N이며 1N 미만이면 0.08rad/s, 그 외 부족분은
0.02rad/s로 보정한다. 0.3N 미만 상실은 보정으로 숨기지 않고 먼저 중단한다.
주는 손은 받는 손의 파지 확인 후, 받는 손은 테이블 지지 확인 후에만 유지 제어를 해제한다.
내려가는 중과 테이블 지지 확인 중에도 오른손의 양쪽 파지력을 검사한다.

전체 왼손 집기 → 오른손 인계 → 내려놓기는 MuJoCo 3.8.1에서
**126.350초 → 84.674초**, 약 33% 짧아졌다. 집게 닫기 구간도 약 20초씩에서 약 4–5초씩으로
줄었다. 최대 패드 접촉력은 2.677N, 최대 관통은 0.0645mm, 물리 경고는 0이었다.
최종 블록 중심은 `[.218911, -.079461, .019999] m`다. 비공개 실행 결과는
`recording/simulation/20260909/pgripper-smooth-left-03/`에 남겼다.
관절 속도·가속도·jerk 제한과 septic 보간은 유지하며, 경유점에서 무조건 일정 속도로
통과하는 새 blending planner를 넣은 것은 아니다.

MuJoCo **3.3.7·3.8.1 각각 최종 테스트 3개가 통과**했다. 내부의 7개 물리 실행은
양방향 인계 성공, 받는 손 접촉 제거, 인계 해제 중 신호 상실, 전체 3단계 성공,
테이블 지지 상실, 내려놓기 하강 중 오른손 파지 신호 상실이다. 성공한 양방향 인계
직후 패드 접촉을 제거하면 40mm 이상 떨어지는 대조 검사도 유지했다.
전체 task는 100초 미만인지 회귀 검사하며, 실패 검사에서는 접촉·지지 없이 놓기를
시작하지 않는지 확인한다. 독립 읽기 전용 검토도 최종 제어권 전환과 판정 조건을 확인했다.

사용자가 지정한 비공개 오른손 실물 테스트 README·설정·보정 코드·로그도 읽어 대조했다.
저장 기록의 동작은 30Hz, 빈 닫힘 목표 선행량 70tick, 접촉 판단 후 43tick이다.
닫힘 요청이 남아 있고 **연속 샘플 사이 위치 변화가 2tick 이하인 상태가 0.1초 유지**되면
접촉으로 추정한다. 0.1초 전체의 총 이동량이 2tick 이하라는 조건과는 다르다.
이 원리는 빈 공간에서는 빨리 닫고 접촉 뒤에는 제한하는 현재 SIM 접근의 참고 근거로 쓴다.

실물 README의 대략적 개폐 속도는 열기 740tick/s, 닫기 620tick/s다. 4096count/rev 기준
모터 각속도로 환산하면 약 1.135rad/s와 0.951rad/s이며, 현재 SIM의 빈 닫힘 0.20rad/s는
그보다 보수적인 값이다. 이것이 손끝 개구 폭·마찰·실제 파지력을 측정했다는 뜻은 아니다.
실측 엔코더 구간과 CAD 전체 travel도 같지 않아 양끝을 억지로 늘려 맞추지 않았다.

기록의 출력 상한 23.5%와 유지 중 약 18.4%는 토크 Nm나 패드 힘 N의 보정값이 아니다.
따라서 SIM의 힘·마찰·관성·모터 gain을 이 비율로 바꾸지 않았다. 로그는 서로 다른 출력
설정의 측정이 섞여 있고 약 0.5초 간격이라, 그것만으로 30Hz 주기나 0.1초 접촉 감지의
정확성을 검증했다고 하지 않는다. 원시 로그·serial ID·개인 보정은 공개 소스에 복사하지
않았고 실물 접근 명령도 실행하지 않았다. 왼쪽의 범위·방향·장착은 별도 실측 대상이다.
